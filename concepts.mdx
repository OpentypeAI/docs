## Runs

A **run** is one request to `POST /v1/runs`, which leads to at most one routed model call. Its `kind` picks what it returns:

| `kind` | You send | You get |
| --- | --- | --- |
| `decision` | `state` + `questions` | `decision`: a probability for each answer you defined |
| `verdict` (default) | `messages` + `schema` | `verdict`: a JSON document that passed your schema |

Fields that belong to the other kind are refused with `400 invalid_body`. For example, `schema` on a decision or `questions` on a verdict. Unknown fields are refused too. `max_output_tokens` is always required.

### Lifecycle

`state` moves `pending` → `running` → `completed` or `failed`.

- **`200`**: the run is terminal. A completed run carries `verdict` or `decision`, never both.
- **`202`**: you replayed an `Idempotency-Key` whose run is still in flight. Read it later with `GET /v1/runs/{run_id}` or [stream it](/guides/streaming).

### Idempotency

`POST /v1/runs` requires an `Idempotency-Key` header of 1 to 255 bytes. A missing key is `400 idempotency_key_required`.

- **Same key, same body.** You get the stored run back with `replayed: true`. There is no second provider call and no second charge.
- **Same key, different body.** `409 idempotency_conflict`.

Generate one key (a UUID works) per logical request, and **reuse it on every retry** of that request.

### What a run returns

| Field | Meaning |
| --- | --- |
| `run_id` | `run_...` |
| `input_digest`, `output_digest` | Hex SHA-256 of the normalized input and of the answer. Your input text is not stored. |
| `usage` | `input_tokens` and `output_tokens` for the call. |
| `cost_micros` | What the call cost, in integer micro-USD. |
| `cost_basis` | `provider_reported` (the provider's own figure) or `estimated` (catalog prices; always the case when `draws > 1`). |
| `replayed` | `true` when this response came from storage, not from a new call. A replay of a completed run carries the stored answer, `usage`, and `cost_micros`, but not `cost_basis` or `schema_enforcement`, because those are not stored. |

### Limits on every run

| Limit | Value | Refusal |
| --- | --- | --- |
| Request body | 1 MiB | `413 body_too_large` |
| Estimated input | 64,000 tokens | `413 input_too_large` |
| Provider spend per run | 5,000 micro-USD ($0.005) | `503 budget_exhausted` |
| `deadline_ms` | default 30,000, capped at 120,000 | `504 deadline_exceeded` |

### Routing

There is no `model` field. OpenType chooses a route from its catalog based on what the run needs. `capability_hint` lets you narrow the choice to routes with one of these capabilities: `chat`, `reasoning`, `tools`, `vision`, `streaming`, `embedding`, `structured_read`. A hint can only narrow the candidates, never widen a limit. If no route fits, the run fails with `503 no_route_available`.

## Decision questions

`questions` is an object keyed by your own question ids. Each question has a `type`, `instructions`, and `criteria`.

<Tabs>
  <Tab title="noul">
    A yes/no question. `criteria` is optional: `{"true": "...", "false": "..."}` describes each side.

    ```json
    "urgent": {"type": "noul", "instructions": "Does this need a reply within one hour?",
               "criteria": {"true": "outage, legal threat, chargeback", "false": "everything else"}}
    ```

    Answer: `{"type": "noul", "probability": 0.83}`. `probability` is **P(yes)**. There is no `confidence`; it would just be `max(p, 1 - p)`.
  </Tab>
  <Tab title="choice">
    One of N named options. `criteria` maps each option name to a description, or to `null`.

    ```json
    "queue": {"type": "choice", "instructions": "Which queue owns this ticket?",
              "criteria": {"billing": "charges, refunds", "technical": "bugs, errors", "other": null}}
    ```

    Answer: `choice` (the most likely option), `probabilities` keyed **by option name**, and `confidence`.
  </Tab>
  <Tab title="score">
    An ordered level. `criteria` lists the levels from lowest to highest.

    ```json
    "tone": {"type": "score", "instructions": "How upset is the customer?",
             "criteria": ["calm", "annoyed", "furious"]}
    ```

    Answer: `score` is the expected level, **0-indexed** (1.34 lands between `annoyed` and `furious`). `legend` maps each index to your level name. `probabilities` is keyed **by index** (`"0"`, `"1"`, ...), and there is also `confidence`.
  </Tab>
</Tabs>

Every answer may also carry:

- **`label_mass`**: how much of the model's probability landed on your labels at all.
- **`answered_within_labels`**: `false` means the model favoured something other than your labels, so the probabilities you see were renormalized over labels it did not prefer. Do not treat those as calibrated.

### Bounds

| Bound | Value |
| --- | --- |
| Questions per run | 1 to 64 |
| Options or levels per question | 2 to 26 |
| Question id | non-empty and unique, with no `:` or newline |
| `state` + `questions`, encoded | 32 KiB |
| `draws` | 1 to 8 (default 1) |
| `think_tokens` | 0 to 4,096 (default 0) |

A question set outside these bounds is `400 invalid_decision_questions`, and nothing is created or charged.

### Stages: `depends_on`, `ask_if`, `alone`

- `depends_on: ["urgent"]` reads this question after `urgent`, in a later stage.
- `ask_if: {"urgent": ["yes"]}` asks this question only if `urgent` was answered `yes`. Otherwise its answer is `{"type": "skipped", "because": {"question": "urgent", "answered": "no", "required": ["yes"]}}`. Skipped answers are never `null`.
- `alone: true` reads the question on its own rather than together with the others.

The response's `decision.stages` lists the question ids in the order they were read, one array per stage. `question_order` fixes your own order, and it must name exactly the keys of `questions`.

### Draws and thinking

- `draws` averages several independent reads. Each draw is paid for, and multi-draw costs are `estimated`. Extra draws help when you compare a probability to a threshold and it lands close to it.
- `think_tokens` lets the model generate hidden reasoning tokens before it answers. They are billed as output. The response reports `thought_tokens` and `thought_closed`; the reasoning text itself is never returned.

### Provenance

- **`read`**: `slot_constrained` means the answers were read from fixed answer positions, so no out-of-set answer was possible. `reconstructed` means they were recovered from generated text.
- **`model`**: the catalog model that answered.

A decision makes one attempt, with no repair. If no decision-capable route is available, or the provider refuses the question set, the run fails with `503 decision_unavailable`.

## Verdicts

A verdict run sends `messages` (`role`: `user` or `assistant`, and `content`), an optional `system`, and `schema`: a JSON Schema that the answer must satisfy.

```json
{
  "messages": [{"role": "user", "content": "Invoice #4411 from ACME, total 1,250.00 EUR, due 2026-10-15"}],
  "schema": {
    "type": "object",
    "required": ["vendor", "total", "currency", "due_at"],
    "properties": {
      "vendor": {"type": "string"},
      "total": {"type": "number"},
      "currency": {"type": "string", "enum": ["EUR", "USD", "GBP"]},
      "due_at": {"type": "string"}
    },
    "additionalProperties": false
  },
  "max_output_tokens": 200
}
```

- **Every verdict returned has passed your schema.** OpenType allows two attempts (one repair). If neither produces a valid document, the run fails with `503 verdict_schema_violation` and `violations`: up to 10 JSON Pointers to where the document failed. Attempts that were made are billed.
- **Schema bounds.** A schema must be at most 32 KiB, at most 12 levels deep, with at most 64 levels of nesting, at most 512 properties, and `pattern`s of at most 256 characters. External `$ref` is not allowed. Out of bounds is `400 invalid_verdict_schema`, and nothing is charged.
- **`schema_enforcement`** tells you whether the provider or OpenType constrained the answer:

| Value | What bound the answer |
| --- | --- |
| `unconstrained` | Nothing on the provider side. OpenType's validation was the only check. |
| `requested` | The provider was given the schema but cannot enforce it. |
| `forced` | The provider forced the schema slot but did not verify the arguments. |
| `enforced` | The provider constrained decoding to the schema. |

In every case the verdict you receive was validated by OpenType.
